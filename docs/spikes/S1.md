# Spike S1: the video engine

Status: done for this machine (2026-11-13). Phase 1 measured the engine on one machine; phase 2 added
the wazero against wasmtime comparison (section 9) and the pure-Go HEVC decoder with and without its
assembly (4.1); the review rounds re-measured the engine's memory reservation (4.5). Criteria not fully
met, each with the decision taken:

- **4K HEVC decode on the default path** (the sandboxed engine): 3.9 fps (8-bit) and 3.6 fps (10-bit),
  below 4 fps; 4.5 and 3.35 with `-skip_loop_filter all`. Decision (owner, version 1): accepted; HEVC
  stays in the sandbox, loop-filter skipping stays off until S2 or G1 recordings show it costs no
  cells, and the pure-Go decoder is only an opt-in fast path.
- **Memory per instance at 4K decoding**: at most 600 MB in 16 of 21 runs, up to 920 MB in the other
  5. Decision: the engine reserves 512 MiB, which is also its ceiling, and the default worker count
  counts each worker at 920 MB (DESIGN.md section 8).
- **Six targets**: met in M1 (section 11). `internal/video`'s tests, which run the engine (encode,
  decode, probe, sandbox and limit tests), pass on all six CI runners, windows/arm64 included, so
  windows/arm64 is no longer experimental for the engine.
- **Decode time limit**: the spike set none. Decision (review round 3): a 30 s no-progress watchdog
  with close-on-cancel, implemented and tested in M1 stream D (DESIGN.md section 12, SECURITY.md
  section 5). M1 measured close-on-cancel at a 75-91% cost (section 10); the owner chose worker
  processes instead (the engine in a child process with the option off), a separate change.

## 3. Method

All code is in `spikes/s1` (its own Go module, so the root `go.mod` is untouched). `s1` drives the
engine; generated media go to the gitignored `spikes/s1/out/`.

**API, verified by reading the source.** `wasm.Run(ctx, rt, mod, wasm.Args{Name, Args, Stdin, Stdout,
Stderr, Config})` exists in `codeberg.org/gruf/go-ffmpreg/wasm` as described. `Name` becomes `argv[0]`
and the single `ffmpreg` program dispatches on it to ffmpeg or ffprobe. `wasm.NewRuntime(ctx, cfg)`
enables SIMD, bulk memory, non-trapping float-to-int, mutable globals, reference types, sign
extension, and the experimental exception-handling, extended-const and tail-call features, and
registers `env.__wasm_setjmp` / `__wasm_longjmp` (implemented with wazero's experimental snapshotter)
and WASI preview 1. `Config` receives the `wazero.ModuleConfig`; files are reached through
`wazero.FSConfig` directory mounts (`WithDirMount` / `WithReadOnlyDirMount`). The spike mounts one
host directory at `/d`, read-only for decoding. It sets `WithSysWalltime` and `WithSysNanotime`
(wazero's defaults are fake clocks). The module comes from `embed.B()`, which the `embed` package
gunzips in its `init`.

Things found that the documents do not say:

- Importing `codeberg.org/gruf/go-ffmpreg/embed` costs about 0.25 s and 65-85 MB at **every** process
  start, even for `--help`, because its `init` decompresses the module. Calling `embed.Free()` after
  compiling releases it.
- `codeberg.org/gruf/go-ffmpreg/wasm` imports `unsafe` (one `isNil` helper). SECURITY.md's rule covers
  our own packages, so this is allowed, but the reviewer should know.
- The ffmpeg build is optimised for size (`-Oz`, `--enable-small`); a speed-optimised build of the same
  sources is the obvious untried lever if the engine must be faster.

**Clips** (`genclips.sh`, native ffmpeg): random four-level grey cells, 5 x 5 pixels, Gaussian blur
sigma 1, +-4 temporal noise, so the encoder spends its bits as on a recording of a code.

| Clip | Encoder | Target | Measured | Notes |
| --- | --- | --- | --- | --- |
| `c1080p30_h264.mp4` | libx264 medium, High, GOP 30 | 17 Mbit/s | 18.1 Mbit/s, 300 frames | BT.709 tags |
| `c4k60_hevc8.mp4` | libx265 fast, Main, GOP 60 | 53 Mbit/s | 52.8 Mbit/s, 600 frames | Each pattern held for 2 frames |
| `c4k60_hevc10_hlg.mp4` | libx265 fast, Main 10, GOP 60 | 53 Mbit/s | 52.7 Mbit/s, 600 frames | `arib-std-b67`, `bt2020`, `bt2020nc`, limited range; both the native and the engine's ffprobe report these tags |

With a new pattern every frame, x265 could not get below about 70 Mbit/s at 4K even at its highest
quantiser, so the 4K clips hold each pattern for two frames (a 30 fps code filmed at 60 fps).

**Decode** measurements read `pipe:1` raw frames into a byte counter and divide by the frame size. 4K
decodes use the first 120 frames (2 s). "Luma-only" is `-vf extractplanes=y -pix_fmt gray` (or
`gray10le` when the engine's ffprobe reports a 10-bit source). Every decode passes `-noautorotate`.
The native comparison passes `-threads 1`.

**Encode** measurements feed `yuv420p` planes built in Go (never converted by ffmpeg) through `Stdin`,
with `-color_range tv -colorspace bt709 -color_primaries bt709 -color_trc bt709` on input and output
and `-x264-params keyint=1:scenecut=0:bframes=0:cabac=1`. Eight distinct random frames are cycled
(every frame is intra-coded, so the cycle does not change the size). Bits per cell is the MP4 size in
bits over cells x frames (it includes container overhead). The cell check decodes the engine's own
MP4 with the engine, averages the central half of each cell, and takes the nearest default level of
FORMAT.md section 7.

**Memory**: "wasm" is the peak size of the instance's linear memory, recorded through
`experimental.WithMemoryAllocator`; "RSS" is the process's `VmHWM`.

## 4. Results in detail

### 4.1 Decode speed

One instance, frames per second (embedded engine unless stated):

| Clip | Full 4:2:0 | Luma-only | Luma, skip loop filter | Native ffmpeg, 1 thread, luma | gen2brain/h265, 1 core |
| --- | --- | --- | --- | --- | --- |
| 1080p30 H.264 | 19.6, 21.0 | 22.2 (21.2-22.9) | 26.5 | 56 (52-59) | n/a (H.264) |
| 4K60 HEVC 8-bit | 3.2, 4.2 | 3.9 (3.5-4.3) | 4.5 (3.8-4.7) | 22.3 (21.7-22.7) | asm 8.6 (8.2-10.2); second session asm 7.3, pure Go 4.7 |
| 4K60 HEVC 10-bit HLG | 2.9 | 3.6 (3.3-4.1) | 3.35 (3.34-3.50) | 19-25 | asm 6.2 (6.2-6.3); second session asm 5.1, pure Go 5.0 |

- The engine is 2.5x slower than single-threaded native ffmpeg on H.264 and 5.7x slower on HEVC.
- The engine columns are the default HEVC path. The luma columns for 4K HEVC are medians of five runs
  over two sessions; the full 4:2:0 column has two runs.
- `gen2brain/h265`, second session (`bench_h265.sh`, decoder `Threads(1)` as in every h265 figure here
  except the one 4-thread run noted below,
  and `GOMAXPROCS=1`, 120 frames, three interleaved
  runs each; the engine measured 3.1-3.5 fps on these clips in the same session, section 9):

  | Clip | With assembly | Pure Go (`-tags noasm`) |
  | --- | --- | --- |
  | 4K HEVC 8-bit | 7.28 (6.88, 7.28, 8.06) | 4.68 (4.26, 4.68, 5.20) |
  | 4K HEVC 10-bit | 5.09 (5.08, 5.09, 5.96) | 4.97 (4.23, 4.97, 5.25) |

  The assembly matters for 8-bit (1.6x) and hardly for 10-bit. Peak RSS of the whole process, which
  also holds the 86 MB stream: 203-338 MB.
- `gen2brain/h265` produced luma identical, byte for byte, to the engine's for all 120 frames of both
  4K clips, in both builds. It reads an Annex B stream (the spike made one with native ffmpeg `-c copy -bsf:v
  hevc_mp4toannexb`; the engine can do the same copy). For comparison only, one run with `Threads(4)`
  (with assembly, 8-bit) decoded at 30.5 fps; no other h265 figure here used more than one thread.
- **Does skipping the loop filter hurt reading cells?** The decoded clips were classified against the
  generated symbols (`s1 classify`). Cell error rates, without / with `-skip_loop_filter all`: 4K HEVC
  23.7% / 23.3% (the 4K clip is past the recorder's capacity, so the absolute rate is high); 1080p
  H.264 2.38% / 2.57%. The effect is small on this synthetic content; real recordings (S2) should
  confirm before it is used.

### 4.3 Streaming

`s1 stream`: Go writes deterministic `yuv420p` frames into the engine's `Stdin` through an `io.Pipe`;
the engine runs `-f rawvideo -i pipe:0 -c:v rawvideo -f rawvideo pipe:1`; Go reads `Stdout` and
compares every byte with the expected frame.

| Run | Data | Throughput | RSS | Mismatches |
| --- | --- | --- | --- | --- |
| 1080p | 10.00 GB (3,215 frames) | 2,071 MB/s | peak 182 MB | 0 |
| 1080p, consumer sleeps 0.5 s every 100 frames | 10.00 GB | 468 MB/s | 194 MB at every sample (4 samples) and peak 195 MB | 0 |
| 4K | 9.99 GB (803 frames) | 1,878 MB/s | peak 325 MB | 0 |

Backpressure works through the pipe in both directions, memory is constant and nothing deadlocked.
The real pipelines also stream: every encode measurement fed frames through `Stdin`, and every decode
measurement read frames from `Stdout`.

### 4.4 Parallel instances

One compiled module, N goroutines each running its own instance (luma-only decode, `-pages 8192`):

| Clip | 1 | 4 (efficiency) | 8 | 16 |
| --- | --- | --- | --- | --- |
| 1080p H.264, aggregate fps | 22.2 | 98.8 (111%) | 137 (77%) | 189 (53%) |
| 4K HEVC 8-bit | 3.9 | 17.8 (114%) | 21.8 (70%) | 30.0 (48%) |
| 4K HEVC 10-bit | 4.06 | 16.5 (102%) | 16.8 (52%) | 25.6 (39%) |

Base of each efficiency figure: the "1" column, which is the median of the three single-instance runs
of the same `bench_repeat.sh` batch as the 4-instance runs (1080p: 21.2, 22.2, 22.9; 4K 8-bit: 3.82,

without the memory reservation.

### 4.5 Memory

| Instance | Wasm linear memory, peak | Process RSS, one instance |
| --- | --- | --- |
| Decode 1080p H.264 | 42 MB | 211 MB (one run of three: 690 MB) |
| Decode 4K HEVC 8-bit | 155 MB | 319-336 MB reserved; 592-698 MB not reserved |
| Decode 4K HEVC 10-bit | 252 MB | 414-436 MB reserved (920 MB in 3 of 9 review-round runs); 958-1,095 MB not reserved |
| Encode 1080p x264 | 46 MB | 263-308 MB |
| Encode 4K x264 8-bit | 140 MB | 591-605 MB (not reserved) |
| Encode 4K x264 10-bit | 237 MB | 816 MB not reserved; 405 MB with 1 GiB and 414 MB with 1.5 GiB reserved |
| Encode 1080p libaom 10-bit, good, cpu-used 6 | 724 MB | 3,061 MB |
| Process with the compiled module, idle | | 171-178 MB |

**Reserve linear memory up front.** wazero's default grows a module's memory by reallocating a Go
slice; the old copies are garbage, and Go's collector lets the heap reach about twice the live size
before collecting, so one 4K 10-bit decoder showed 1.1 GB RSS for 252 MB of linear memory. With
`RuntimeConfig.WithMemoryLimitPages(n).WithMemoryCapacityFromMax(true)` the backing slice is
allocated once at its maximum and never moved; untouched pages are not resident, and the same decoder
peaks at 415 MB. Some runs still reach far more: when Go reuses and zeroes an earlier span for the
reservation, the whole reservation becomes resident. Over all recorded single-instance 4K decodes
with 512 MiB reserved, RSS was 319-436 MB in 16 of 21 runs and 685, 825, 920, 920 and 920 MB in the
other 5 (920 MB = the process plus the whole 512 MiB). An allocator built on `mmap` / `VirtualAlloc`
(through `experimental.WithMemoryAllocator`) would make lazy commitment certain.

**512 MiB or 1 GiB?** SECURITY.md section 5 had a 1 GiB decoding ceiling. In the review round the 4K
10-bit decode (60 frames) was run nine times with 512 MiB and six times with 1 GiB reserved:
512 MiB gave 414-434 MB, and 920 MB in 3 runs; 1 GiB gave 414-436 MB, and 1,434 MB in 1 run. A larger
reservation therefore raises the worst case by its own size. 512 MiB is enough for every decode
measured (252 MB in use) and every x264 encode (238 MB), so it is the single value for decoding and
encoding, both the reservation and the ceiling (SECURITY.md section 5, DESIGN.md sections 8 and 12).
Only libaom's good-quality AV1 encoder needed more (724 MB); it is not used.

Marginal RSS per added 4K decoder, from the 4-instance runs with reservation: 150-320 MB (8-bit),
240-420 MB (10-bit).

### 4.7 Six targets

`CGO_ENABLED=0 go build -trimpath` succeeds for linux/amd64 (static ELF), linux/arm64, darwin/amd64,
darwin/arm64, windows/amd64 and windows/arm64, 17-18 MB each, including gen2brain/h265. Only
linux/amd64 was run. The repository's CI (after PR #1 on main) passes the golden vectors and the
static build on all six runners: ubuntu-24.04, ubuntu-24.04-arm, macos-26, macos-26-intel,
windows-2025 and windows-11-arm. The engine itself, and this spike, have not run on the other five.

windows/arm64, from wazero v1.12.0's source: `internal/platform.compilerPlatformSupports` returns true
for `windows` with `GOARCH == "arm64"` unless the threads feature is enabled (it is not), and
`executableMmapSupported` uses `VirtualAlloc` / `VirtualProtect` on Windows, so `NewRuntimeConfig`
selects the **compiler**, not the interpreter. The arm64 backend never allocates x18
(`internal/engine/wazevo/backend/isa/arm64/abi.go`), which Windows on arm64 reserves for the thread
environment block, so the obvious ABI hazard is avoided. Whether it runs correctly is untested. For
scale, the interpreter on this machine decodes 1080p H.264 at 0.32 fps (70x slower than the compiler),
so an interpreter fallback would not be usable.

## 9. wazero against wasmtime (phase 2)

**Result: wasmtime is 1.22-1.30x faster than wazero, well under 2x. The stop condition is not met.**

Method: the module of go-ffmpreg v0.6.22 (`embed/ffmpreg.wasm.gz`, decompressed, 20,324,330 bytes,
SHA-256 `357dd97d...bc766`) was precompiled with `wasmtime compile -W
exceptions=y,tail-call=y,simd=y,extended-const=y` (wasmtime 50.0.1) and run with `wasmtime run ...
,unknown-imports-trap=y --allow-precompiled --dir out::/d --argv0 ffmpeg`. The module imports
`env.__wasm_setjmp` and `env.__wasm_longjmp`, which go-ffmpreg implements on the host; under wasmtime
they trap if called, and no decode here called them. Arguments, clips and frame counts are those of
wazero (`s1 decode -pages 8192`): 300 frames of the 1080p clip, 120 of each 4K clip, one instance,
output to a pipe, three interleaved runs. The wasmtime time is the whole process (including its
start-up with the precompiled module, about 0.1 s); the wazero time excludes compilation. Both
produced byte-identical output (SHA-256 of 5 decoded 4K frames).

| Clip, output | wazero fps (median; runs) | wasmtime fps (median; runs) | wasmtime / wazero |
| --- | --- | --- | --- |
| 1080p H.264, luma | 18.5 (18.0, 18.5, 19.4) | 22.7 (20.8, 22.7, 26.6) | 1.22 |
| 1080p H.264, full 4:2:0 | 18.7 (17.8, 18.7, 19.2) | 23.6 (21.1, 23.6, 24.5) | 1.26 |
| 4K HEVC 8-bit, luma | 3.45 (3.30, 3.45, 3.49) | 4.37 (4.19, 4.37, 4.82) | 1.27 |
| 4K HEVC 8-bit, full 4:2:0 | 3.45 (3.32, 3.45, 3.51) | 4.40 (4.27, 4.40, 4.45) | 1.28 |
| 4K HEVC 10-bit HLG, luma | 3.13 (2.88, 3.13, 3.19) | 4.08 (3.85, 4.08, 4.13) | 1.30 |
| 4K HEVC 10-bit HLG, full 4:2:0 | 3.15 (3.10, 3.15, 3.19) | 3.98 (3.60, 3.98, 4.52) | 1.26 |

These wazero figures are about 10% below those of section 4.1, taken earlier in the day; the machine

(IMPLEMENTATION_PROMPT.md section 5): wazero misses the 4K decode threshold, but wasmtime is less than

## 10. Cost of `WithCloseOnContextDone` (M1 stream D)

DESIGN.md section 12 asked for the S1 decode and encode figures with the runtime option on and off.
**The cost is 75-91%, far above the 10% that goes to the owner.**

Method: `internal/video/s1bench_test.go` (build tag `s1bench`), on the machine of section 2. Two
runtimes compile the same module, one with the option on and one off, both with 512 MiB reserved and
the compilation cache; each figure alternates off and on three times and gives the median. Decodes are
luma-only (`extractplanes=y`, `gray` or `gray10le`) to a pipe, as in 4.1; encodes are the tuned x264
settings of 4.2 at qp 32 from `yuv420p` planes built in Go. The clips were remade with native ffmpeg
6.1.1 from `lavfi` sources with the recipe of section 3 (5-pixel random grey cells, Gaussian blur
sigma 1, +-4 temporal noise, the 4K patterns held two frames): 1080p30 H.264 at 18.6 Mbit/s, and 4K60
HEVC 8-bit and 10-bit HLG at 54 Mbit/s, 180 frames each.

```sh
QRVT_S1_CLIPS=dir go test -tags s1bench -run S1 -v -timeout 3h ./internal/video/
```

| Measure | Option off, fps (runs) | Option on, fps (runs) | Cost |
| --- | --- | --- | --- |
| Decode 1080p30 H.264, luma, 300 frames | 22.33 (22.12, 22.33, 22.65) | 5.55 (5.59, 5.39, 5.55) | 75% |
| Decode 4K60 HEVC 8-bit, luma, 120 frames | 3.08 (3.15, 2.93, 3.08) | 0.28 (0.28, 0.28, 0.29) | 91% |
| Decode 4K60 HEVC 10-bit HLG, luma, 120 frames | 3.02 (2.72, 3.02, 3.18) | 0.29 (0.24, 0.29, 0.29) | 90% |
| Encode 1080p, tuned x264, 60 frames | 7.66 (7.79, 7.53, 7.66) | 0.87 (0.87, 0.84, 0.87) | 89% |
| Encode 4K, tuned x264, 16 frames | 2.08 (1.98, 2.08, 2.08) | 0.22 (0.22, 0.22, 0.21) | 89% |

An earlier run of the 1080p decode gave 19.38 off and 4.61 on (76%). The off figures agree with
sections 4.1 and 4.2 within this machine's variance.

**Cause.** In wazero v1.12.0 the option makes the compiler emit, at the head of every Wasm loop, a
load of a trampoline address and an indirect call to it (`internal/engine/wazevo/frontend/lower.go`,
the `wasm.OpcodeLoop` case, `if c.ensureTermination`), so every iteration of every loop pays a call.
ffmpeg's decoders and x264, compiled with `-Oz` and no assembly, spend their time in tight loops. A
crafted HEVC stream whose decoding is mostly picture-filling loops ran 13 times slower (1.1-1.3 s off,
15-17 s on). The option also cannot interrupt code on its own: the check reads a flag set by another
goroutine, and compiled Wasm cannot be preempted by the Go scheduler, so instances on every P starved
that goroutine on the 4-vCPU CI runners (a 30 s stall stopped only after 79 s). `internal/video` now
runs at most GOMAXPROCS - 1 instances at once.

**Decision (owner).** The option stays on in M1 so that nothing is fast and unguarded; the hang
guard moves to worker processes (each engine instance in a child process with the option off, killed
by the watchdog), a separate change. For comparison, a prototype on this machine (a test binary
re-executing itself as the child) measured: start-up to engine loaded from the compilation cache
0.48-0.60 s (5 runs); frames through the OS pipe at 10-13 ms per 4K 8-bit luma frame (630-800 MB/s)
and 36-37 ms per 4K 10-bit 4:2:0 frame (670-690 MB/s), against 1.6 and 7.1 ms through an in-process
`io.Pipe`, that is about 3-4% and 11% of the 4K decode time per frame (330 ms) before any overlap.
